# Order — Domain Document

Version: 1.0
Status: Accepted
Established: August 2026
Authors: Michal Guoth, Gunimi Architecture

---

## Purpose

This document defines Order as a first-class domain entity within Gunimi's business
reality model. It derives from DOMAIN_MODEL.md, DOMAIN_LAWS.md, and ADR-002 through
ADR-005.

**Order is the first entity designed entirely under the new constitutional model.**
It is the first real proof that Reality Principle, Assignment, Relationship, Event,
Memory, and Signal can work together without workarounds. If Orders can be built
without `owner_id`, without ad-hoc FKs treated as philosophy, without CRUD→Signal
hacks, and without violating any Domain Law — the foundation is valid.

---

## Why Order Is an Entity

An entity must satisfy all three conditions from DOMAIN_MODEL.md:

1. **Own identity** — an Order has a unique number (ORD-0001), can be referred to,
   tracked, and uniquely identified across its entire lifecycle
2. **Own lifecycle** — an Order is created, progresses through states, and ends
   (completed or cancelled) independently of the Person, Company, or Deal it relates to
3. **Own history** — Events happen *to* an Order: items are added, status changes,
   value is updated, responsibility is transferred

Order passes all three. It is a domain entity.

---

## The Reality Principle Applied

An Order exists in business reality before Gunimi records it. A customer calls, sends
an email, or submits a request. That is a real event. Gunimi's role is to capture,
track, and understand that reality — not to define it.

An Order is:
- A real commercial commitment between an Organization and a Business Entity
- An object with monetary value, line items, agreed terms, and a due date
- A subject of responsibility (who handles it), communication (has it been acknowledged),
  and history (how did it evolve)

An Order is not:
- A task (a task is an internal action; an Order is an external commercial fact)
- A deal stage (a Deal is an opportunity; an Order is a confirmed or near-confirmed
  commercial transaction)
- A notification or reminder (those are derived artifacts)

## Schema

### workspace_orders

```sql
workspace_orders
  id                    UUID PRIMARY KEY
  workspace_id          UUID NOT NULL REFERENCES workspaces(id)

  -- Identity
  number                TEXT NOT NULL          -- ORD-0001, generated by system
                                               -- never user-authored, never editable
  title                 TEXT NOT NULL
  notes                 TEXT

  -- Money
  currency              TEXT NOT NULL DEFAULT 'EUR'
  -- total_amount is never stored — always computed from order items
  -- See: Money Model section

  -- Lifecycle state (independent dimension)
  status                TEXT NOT NULL DEFAULT 'draft'
  -- draft | confirmed | in_progress | completed | cancelled

  -- Communication state (independent dimension — see: Two State Machines)
  communication_state   TEXT NOT NULL DEFAULT 'not_sent'
  -- not_sent | sent | acknowledged

  -- Temporal
  due_date              DATE
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
  updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()

  -- Compatibility bridges (see: Relationship Compatibility section)
  company_id            UUID REFERENCES workspace_companies(id)
  contact_id            UUID                   -- see: workspace_people compatibility note
  deal_id               UUID REFERENCES workspace_deals(id)

  -- NO owner_id — responsibility is modeled via workspace_assignments (ADR-005)
```

### workspace_order_items

```sql
workspace_order_items
  id                    UUID PRIMARY KEY
  order_id              UUID NOT NULL REFERENCES workspace_orders(id) ON DELETE CASCADE
  description           TEXT NOT NULL
  quantity              NUMERIC(10, 3) NOT NULL DEFAULT 1
  unit_price            INTEGER NOT NULL        -- minor currency units (cents)
                                               -- NEVER floating point (see: Money Model)
  discount_percent      NUMERIC(5, 2) NOT NULL DEFAULT 0   -- 0.00 to 100.00
  tax_rate_percent      NUMERIC(5, 2) NOT NULL DEFAULT 0
  position              INTEGER NOT NULL DEFAULT 0          -- sort order
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()

  -- COMPUTED on read (never stored):
  -- line_total = quantity * unit_price * (1 - discount_percent/100) * (1 + tax_rate_percent/100)
  -- order total = SUM(line_total) across all items for this order
```

## Money Model

**Rule: Money is never stored as floating-point.**

All monetary values are stored as `INTEGER` in minor currency units (cents, haléře,
eurocenty). This eliminates floating-point rounding errors in commercial contexts
where precision is legally and contractually required.

```
EUR 42.50 → stored as 4250
EUR 0.99  → stored as 99
EUR 420.00 → stored as 42000
```

**Rule: Total amount is never user-authored and never stored.**

`total_amount` does not exist as a column. It is always computed:

```
line_total = quantity × unit_price × (1 − discount_percent/100) × (1 + tax_rate_percent/100)
order_total = Σ line_total for all items
```

The computation lives in the data access layer, not in the UI. The user sees totals;
the user never writes them.

## Two State Machines

Order carries two independent state dimensions. They must never be collapsed into one.

### Dimension 1: Order Lifecycle

What is the current operational state of this Order?

```
draft → confirmed → in_progress → completed
                               ↘ cancelled
```

| State | Meaning |
|---|---|
| `draft` | Order exists but is not yet committed |
| `confirmed` | Terms agreed; work/delivery may begin |
| `in_progress` | Active execution underway |
| `completed` | Delivered and closed |
| `cancelled` | Withdrawn before completion |

### Dimension 2: Communication State

Has the counterparty acknowledged this Order?

```
not_sent → sent → acknowledged
```

| State | Meaning |
|---|---|
| `not_sent` | Order exists but has not been communicated to the counterparty |
| `sent` | Order has been sent (email, document, portal) |
| `acknowledged` | Counterparty has confirmed receipt or acceptance |

**Why separate?**

An Order can be `confirmed` and `not_sent` simultaneously — the internal team has
committed, but the document hasn't gone out yet. An Order can be `in_progress` and
`sent` but not `acknowledged` — delivery has started, but the customer hasn't formally
responded. These are two different truths about the same entity.

Collapsing them into a single status field would require a combinatorial explosion of
states (confirmed_sent, confirmed_acknowledged, in_progress_sent...) or, worse, would
cause one dimension to silently overwrite information about the other.

## Responsibility Model (ADR-005)

**There is no `owner_id` field.**

Responsibility for an Order is modeled through `workspace_assignments`:

```
workspace_assignments
  entity_type  = 'order'
  entity_id    = order.id
  actor_type   = person | team | agent | system
  actor_id     = (references the appropriate table for the actor_type)
  responsibility = owner | collaborator | reviewer | approver | observer
```

### Responsibility vocabulary for Orders

| Responsibility | Meaning in Order context |
|---|---|
| `owner` | Primary accountability — drives the Order to completion |
| `collaborator` | Active contributor — works alongside the owner on delivery |
| `reviewer` | Evaluates Order terms, quality, or compliance |
| `approver` | Has authority to authorize the Order proceeding to next lifecycle state |
| `observer` | Committed to staying informed — receives Signals about this Order without action obligation |

**On `observer`:**

`observer` is a legitimate responsibility, not a permission. A Finance director may
observe an Order without being responsible for its execution. A manager may monitor
multiple Orders across a team without owning any. An AI agent may hold observer
responsibility and generate Signals when patterns emerge.

The distinction from ADR-005 applies: Permission governs what an Actor can see in
the system. Observer responsibility governs what they have committed to track.
These are not the same thing.

### Actor types for Orders

| Actor type | Example |
|---|---|
| `person` | Jan Kováč — individual responsibility |
| `team` | Sales Slovakia — collective responsibility |
| `agent` | Gunimi AI — automated monitoring and suggestion |
| `system` | External ERP — system-level handoff |

An Order in a small firm may have one `person` Assignment with responsibility `owner`.
An Order in an enterprise may have Sales (`owner`), Legal (`reviewer`), Finance (`approver`),
and a department head (`observer`). The model accommodates both without schema changes.

## Relationship Compatibility

Orders connect to Companies, Contacts, and Deals. These connections are business facts
that belong in `workspace_relationships` as first-class entities (ADR-003). However,
`workspace_relationships` migration is a pre-paying-customer milestone, not an Open Alpha
requirement.

**The compatibility bridge pattern (per ADR-003):**

```sql
company_id  UUID REFERENCES workspace_companies(id)   -- compatibility FK
deal_id     UUID REFERENCES workspace_deals(id)        -- compatibility FK
contact_id  UUID                                       -- see: workspace_people compatibility
```

These FKs are explicitly labeled as **compatibility bridges**. They resolve correctly
today. They will migrate to `workspace_relationships` entries with type, status,
valid_from/valid_to, and confidence when the Relationship migration is executed.

**What this means for new feature code:**
- Do not add new FK columns to resolve additional connections
- Do not build UI that treats these FKs as the canonical relationship model
- When displaying "connected company" or "connected contact", route through a resolver
  that will later be upgraded to query `workspace_relationships`

### workspace_people compatibility note

ADR-002 defines `workspace_people` as the unified Identity Layer — the canonical table
for all humans in business reality. However, this migration has not yet been executed.

**Resolution for Orders (same pattern as ADR-005, section "Compatibility with workspace_members"):**

During implementation before the `workspace_people` migration:
- `contact_id` references `workspace_members.id`
- The column is named `contact_id` in the schema, not `member_id`, preserving the
  domain intent
- When the `workspace_people` migration is complete, `contact_id` shifts to reference
  `workspace_people.id` — no semantic change, only the reference target changes

The domain contract — a Person exists independently of their authentication status —
is preserved in naming and intent from the start. The incompleteness is explicit, not
hidden.

## Signal Flow

**Rule: Order Events flow into the Signal Engine. CRUD operations never call createSignal().**

```
Order Event (state transition, item change, due_date passed)
         ↓
   Signal Engine (detects pattern across Events and reality)
         ↓
   Signal (with lifecycle: emerging → active → resolved / dismissed / expired)
```

Signal Engine candidates for Orders (not hardcoded rules — detected patterns):

| Pattern | Signal opportunity |
|---|---|
| Order in `draft` for > N days | Stalled draft — may need attention or cancellation |
| Order `sent` but not `acknowledged` for > N days | Unacknowledged order — counterparty follow-up |
| Order `due_date` passed with status not `completed` | Overdue order |
| Assignment in `proposed` for > 24 hours | Unacknowledged responsibility |
| Order value exceeds threshold, no `approver` Assignment | Missing approval gate |

These are detected by the Signal Engine from Event patterns — not triggered by
`updateOrder()` calling `createSignal()`.

## Paper Walkthrough

This walkthrough tests the model against a real business scenario. Every step must
resolve without violating a Domain Law or requiring a new abstraction.

**Scenario:** A company receives an order request via email.

```
1. Email arrives (Event: email_received)
       ↓
2. Team member clicks "Create Order" in Email detail view
   → Order ORD-0001 created in status draft, communication_state not_sent
   → Title pre-filled from subject, notes from body
   → company_id and contact_id inferred from email sender (compatibility FK)
       ↓
3. Items added manually (or AI suggests from email body if prices detected)
   → Each item: description, quantity, unit_price (in cents), discount, tax
   → Total computed in real time — never stored
       ↓
4. Sales Team assigned as owner (workspace_assignments)
   Finance Team assigned as reviewer
   Department head assigned as observer
   → No owner_id. Three Assignments on the same Order.
       ↓
5. Finance reviews and approves → Order status: confirmed
   (Event: order_status_changed, from: draft, to: confirmed)
       ↓
6. Order sent to customer → communication_state: sent
   (Event: order_communication_sent)
   → Order lifecycle: still confirmed. Communication is a separate dimension.
       ↓
7. Customer replies acknowledging → communication_state: acknowledged
   (Event: order_acknowledged)
       ↓
8. Work begins → Order status: in_progress
   (Event: order_status_changed, from: confirmed, to: in_progress)
       ↓
9. Due date passes without completion
   → Signal Engine detects: due_date < now AND status ≠ completed
   → Signal created: order_overdue (lifecycle: emerging)
   → Observer (department head) is informed
   → Owner (Sales) receives actionable Signal
       ↓
10. Order delivered → status: completed
    (Event: order_status_changed, from: in_progress, to: completed)
    → Signal order_overdue resolved (lifecycle: resolved)
    → Event: order_completed → feeds Memory layer with provenance
```

**Verification:** No Domain Law violated. No `owner_id`. No `createSignal()` in CRUD.
Two state machines independent. Money in cents. Responsibility distributed across
three Assignments. Signal Engine detected pattern from Events, not from application code.

The model holds.

## Entity Map Position

```
Order (workspace_orders)
  ├─ workspace_assignments    responsibility model (owner, collaborator, reviewer, approver, observer)
  ├─ workspace_order_items    line items (computed totals, never stored)
  ├─ Events                   immutable state transitions and facts (Law IV)
  ├─ Signals                  via Signal Engine only — never via CRUD
  ├─ Memory                   AI interpretation of Order history (with provenance — Law II)
  └─ Relationship connections (future: workspace_relationships)
      ├─ company_id FK        compatibility bridge — present
      ├─ contact_id FK        workspace_members.id now → workspace_people.id post-migration
      └─ deal_id FK           compatibility bridge — present
```

## What This Document Is Not

This document is not a database schema. The schema above is the current implementation
form of the domain model. If the implementation contradicts this document, the
implementation is wrong.

This document is not a UI specification. UI surfaces present role-aware perspectives
on Order reality. They never define it.

This document is not a migration plan. The compatibility bridge pattern and the
workspace_people migration path are referenced but not specified here. They are governed
by ADR-002, ADR-003, and their respective migration documents.

## Constraints and Non-Goals

**Constraints (apply immediately):**
- No `owner_id` field. No `assigned_to` field. Ever.
- Money stored as INTEGER in minor currency units. No exceptions.
- Total amount never stored. Always computed.
- Lifecycle and communication_state are always two separate columns.
- Signal generation always flows through Signal Engine.

**Deferred (explicitly not in this version):**
- PDF generation
- Payment processing or Stripe integration
- Email sending to counterparty from within Gunimi
- Full `workspace_relationships` migration for Order connections
- Bi-temporal queries on Order history
- Order templates

Deferred items are not architectural decisions — they are product scope decisions.
The schema is designed to accommodate them without breaking changes.

## Domain Law Compliance

| Law | Compliance |
|---|---|
| I — No duplication | One Order record per Order in reality |
| II — Memory provenance | Order Memory traces to Order Events |
| III — Relationship has two participants | Order→Company via Relationship (two entities) |
| IV — Events immutable | Order state transitions recorded as immutable Events |
| V — Role changes perspective | Sales and Finance see same Order; role determines emphasis |
| VI — Identity independent of auth | contact_id → workspace_people (not auth.users) |
| VII — Business Entity ≠ Organization | Order counterparty is always a Business Entity |
| VIII — AI never creates reality | AI may suggest items from email; human confirms |
| IX — Memory decays | Order Memory has provenance and confidence rating |
| X — Wisdom not hardcoded | Signal patterns detected, not authored |
| XI — Person exists once | contact_id is singular per workspace_people record |
| XII — Signals have lifecycle | order_overdue: emerging → active → resolved |

All twelve Domain Laws: compliant.
